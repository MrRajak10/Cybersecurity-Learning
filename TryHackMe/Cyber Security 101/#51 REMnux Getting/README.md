# REMnux Getting Started — TryHackMe

This repository contains beginner-friendly learning notes for the **REMnux Getting Started** room from the TryHackMe Cyber Security 101 learning path.

The room provides a practical introduction to **REMnux**, a Linux distribution designed for analyzing potentially malicious software and artifacts. Instead of focusing only on obtaining answers, this repository focuses on understanding the analysis process, the purpose of each tool, and how the techniques connect to real-world malware analysis and digital forensics.

## What Is REMnux?

REMnux is a Linux distribution designed specifically for **reverse engineering and malware analysis**.

Instead of manually installing and configuring many separate analysis utilities, REMnux provides a prepared environment containing tools useful for investigating:

* Malicious documents
* Executables
* Memory images
* Network activity
* Scripts
* Encoded or obfuscated data

A major benefit is isolation. Malware analysis can be dangerous when performed directly on a normal workstation. A dedicated analysis environment makes it easier to investigate suspicious artifacts while reducing the risk to the analyst's primary system.

## Room Structure

The room introduces three major areas of analysis:

### 1. File Analysis

A potentially malicious Excel document is examined using **oledump.py**.

The analysis demonstrates how an Office document can contain embedded streams and VBA macros. Rather than treating the document as a normal spreadsheet, the analyst examines its internal structure and looks for code that may execute when the document is opened.

The important concept is:

```text
Office document
      ↓
OLE / Compound File structure
      ↓
Data streams
      ↓
VBA project
      ↓
Macro code
      ↓
Potential execution behavior
```

This is an example of **static analysis** because the file is examined without executing the suspected malicious content.

---

## OLE and Compound File Analysis

Older Microsoft Office formats commonly use the **Compound File Binary Format**, sometimes referred to as OLE structured storage.

A single document can contain multiple internal streams, such as:

* Document data
* Metadata
* VBA project information
* Other embedded objects

`oledump.py` is useful because it allows an analyst to inspect those streams and identify potentially interesting content.

One important observation is the presence of a stream marked with **`M`**, which indicates the presence of a VBA macro stream.

This gives the analyst a useful investigation path:

```text
Find suspicious document
        ↓
Inspect streams
        ↓
Identify macro stream
        ↓
Extract/decompress VBA
        ↓
Read the macro
        ↓
Determine what the macro attempts to do
```

---

## VBA Macro Analysis

The room demonstrates that macro code can contain much more than spreadsheet automation.

A malicious macro may:

1. Start PowerShell.
2. Modify PowerShell execution behavior.
3. Download another file from the Internet.
4. Store the downloaded file temporarily.
5. Execute the downloaded file.

A simplified representation is:

```text
User opens document
        ↓
Macro executes
        ↓
PowerShell starts
        ↓
Remote resource requested
        ↓
Payload downloaded
        ↓
Payload saved locally
        ↓
Payload executed
```

This is important because the original Office document may only be the **initial delivery mechanism**. The actual malicious payload can be downloaded later.

## Suspicious PowerShell Concepts

The room introduces several PowerShell concepts that are important during malware analysis.

### `-WindowStyle Hidden`

This can cause the PowerShell window to run without being visibly presented to the user.

It has legitimate administrative uses, but malware can abuse the same behavior to make execution less noticeable.

### `-ExecutionPolicy Bypass`

This can be used to bypass normal PowerShell execution-policy restrictions for the current execution context.

Again, execution-policy bypassing is not inherently malicious, but seeing it combined with downloading and executing an unknown payload should increase suspicion.

### `Invoke-WebRequest`

This PowerShell command can retrieve content from a remote URL.

In malware investigations, analysts should pay particular attention when it is used to retrieve:

* Executables
* Scripts
* Archives
* Secondary payloads

### `-OutFile`

This allows downloaded content to be written to a local file.

### `Start-Process`

This can be used to launch another process.

Combining these behaviors creates a recognizable malware pattern:

```text
Download → Save → Execute
```

That pattern is much more important to remember than memorizing an individual command.

---

## Why CyberChef Is Useful

Malware frequently uses obfuscation to make scripts harder to understand.

CyberChef can help analysts transform suspicious data into a more readable representation.

For example, a script may replace placeholder characters before the actual command becomes readable. The room demonstrates using **Find / Replace** operations to undo simple transformations.

The broader lesson is:

> Do not assume that unreadable text is encrypted. It may simply be encoded, substituted, escaped, or obfuscated.

During analysis, the analyst should ask:

* What transformation was applied?
* Can it be reversed?
* Does the transformed value reveal a command?
* Does it reveal a URL, filename, IP address, or payload?

# Dynamic Analysis and INetSim

Static analysis tells us what a file **appears capable of doing**.

Dynamic analysis helps us observe what it **actually attempts to do while running**.

One of the most important behaviors to monitor is network communication.

Real malware may attempt to contact:

* Command-and-control servers
* Download servers
* Payload hosting infrastructure
* DNS services
* Other attacker-controlled systems

Allowing unknown malware to communicate directly with the Internet is dangerous.

This is where **INetSim** becomes useful.

---

## What Is INetSim?

INetSim is an **Internet services simulation suite**.

It can simulate common network services so that suspicious software can interact with a fake environment instead of a real Internet infrastructure.

Conceptually:

```text
Suspicious program
        ↓
Attempts Internet connection
        ↓
INetSim intercepts/simulates service
        ↓
Analyst observes request
```

This allows an analyst to study network behavior without necessarily giving the sample unrestricted access to the Internet.

---

## Why a Fake Network Matters

Suppose a suspicious program attempts to download a second payload.

Instead of allowing:

```text
Malware → Real Internet → Attacker Server
```

an analysis environment can provide:

```text
Malware → Simulated Network → INetSim
```

The analyst can then inspect:

* Requested URLs
* Protocols
* HTTP methods
* Download attempts
* Other network interactions

This is especially valuable during malware triage.

---

## Simulating a Malware Download

The room demonstrates how a command-line download can be used to mimic behavior frequently observed in malware.

The important concept is not the exact payload name.

The important behavior is:

```text
Initial file
    ↓
Contacts server
    ↓
Requests second-stage file
    ↓
Downloads file
    ↓
Uses downloaded content
```

This is commonly called **second-stage payload delivery** or **multi-stage execution**.

A single malicious document therefore does not necessarily contain the entire attack. It may simply serve as the first step.

---

# INetSim Connection Reports

One of the useful features of INetSim is its ability to generate reports of simulated network activity.

These reports can help analysts reconstruct what happened during execution.

Useful information may include:

* Connection details
* Requested URLs
* Protocols
* HTTP methods
* Requested files

This demonstrates an important forensic principle:

> Evidence should be collected and preserved so that analysis can be performed systematically after execution.

# Memory Forensics with Volatility 3

The room also introduces **memory analysis**.

When a system is compromised, valuable evidence may exist only in RAM.

Examples include:

* Running processes
* Process relationships
* Command-line arguments
* Loaded modules
* File objects
* Suspicious processes
* Potential injected code

A memory image can therefore provide evidence that may not be available from disk alone.

---

## Why Memory Forensics Matters

Consider a malicious process that executes entirely in memory.

A traditional disk investigation might fail to reveal enough evidence.

Memory analysis can potentially expose:

```text
Process
   ↓
Parent process
   ↓
Command-line arguments
   ↓
Loaded modules
   ↓
Memory-resident artifacts
```

This makes memory forensics an important part of incident response.

---

# Important Volatility 3 Plugins

The room introduces several Windows-focused plugins.

## `windows.pstree`

Displays processes in a tree structure based on parent-child relationships.

This helps analysts understand:

```text
Parent Process
      ├── Child Process
      │      └── Suspicious Child
      └── Another Process
```

Unexpected parent-child relationships can be valuable indicators during investigations.

---

## `windows.pslist`

Lists active processes found in the memory image.

This provides a basic process inventory.

---

## `windows.psscan`

Scans memory for process structures and can identify processes that may not appear in a normal active-process listing.

This is useful because relying on a single process listing can miss important evidence.

---

## `windows.cmdline`

Displays command-line arguments associated with processes.

Command-line arguments can reveal:

* Scripts being executed
* Parameters
* URLs
* Suspicious commands
* Execution paths

The command line can therefore provide much more context than a process name alone.

---

## `windows.filescan`

Scans the memory image for file objects.

This can uncover references to files that are relevant to the investigation.

---

## `windows.dlllist`

Lists DLLs/modules associated with processes.

This can help analysts investigate what executable components are loaded into a process and identify unusual module paths.

---

## `windows.malfind`

Searches for characteristics associated with potentially injected code or suspicious memory regions.

It can be useful when investigating techniques such as:

* Process injection
* Suspicious executable memory
* In-memory code

However, findings from `malfind` should be treated as **investigative leads**, not automatic proof of malicious activity.

---

# Evidence Pre-Processing

The room highlights an important forensic workflow: **pre-process evidence before performing detailed investigation**.

Instead of repeatedly running every forensic command manually, an analyst can generate outputs in advance and save them for later searching and comparison.

For example:

```text
Memory image
     ↓
Volatility plugins
     ↓
Text/JSON output
     ↓
Saved evidence
     ↓
Faster investigation
```

This is especially useful for large memory images.

---

## Automating Volatility Analysis

The room demonstrates a shell `for` loop that runs multiple Volatility plugins automatically.

The general concept is:

```text
For each plugin:
    run Volatility
    save the output
    move to the next plugin
```

This eliminates repetitive manual execution.

Automation is an important analyst skill because incident-response work often involves processing large amounts of evidence.

# String Extraction

The Linux `strings` utility is also introduced.

It can extract printable text from binary data.

The room demonstrates extracting different string formats, including:

* ASCII-style strings
* 16-bit little-endian strings
* 16-bit big-endian strings

Strings can sometimes reveal useful artifacts such as:

* URLs
* File paths
* Commands
* Usernames
* Registry information
* Error messages
* Configuration data

However, strings alone should not be treated as definitive evidence. They are another source of investigative clues.

# Static vs Dynamic Analysis

One of the biggest concepts introduced by this room is the distinction between static and dynamic analysis.

| Static Analysis                      | Dynamic Analysis                          |
| ------------------------------------ | ----------------------------------------- |
| Examines a file without executing it | Observes behavior during execution        |
| Looks at internal structure          | Looks at runtime activity                 |
| Can reveal macros and embedded code  | Can reveal network/process behavior       |
| Lower execution risk                 | Requires controlled execution environment |
| Example: `oledump.py`                | Example: INetSim                          |

In real investigations, these approaches complement each other.

A useful workflow is:

```text
Sample
  ↓
Static Analysis
  ↓
Identify suspicious behavior
  ↓
Controlled Dynamic Analysis
  ↓
Observe runtime activity
  ↓
Memory / Network Evidence
  ↓
Correlate findings
```

# Challenges and Learning Lessons

The most important learning challenges in this room are conceptual rather than tool-specific.

### Understanding nested behavior

At first, a malicious Office document may appear to be only a spreadsheet.

After inspecting it, the analyst discovers:

```text
Document
→ VBA macro
→ PowerShell
→ Network request
→ Downloaded payload
→ Execution
```

Thinking in terms of this execution chain is an important malware-analysis skill.

### Understanding unfamiliar output

Tools such as `oledump.py` and Volatility can generate a large amount of information.

A beginner does not need to understand every line immediately.

A better approach is to identify:

1. What does the plugin/tool output?
2. Which fields are relevant?
3. What evidence supports the current hypothesis?
4. What should be investigated next?

### Learning to investigate rather than memorize

The room is more valuable when the commands are understood conceptually.

For example:

```text
windows.pstree
```

is not merely a command to memorize.

The real lesson is:

> Processes form relationships, and those relationships can reveal suspicious execution chains.

# Beginner Practice Activities

## Practice 1 — Identify Suspicious Macro Behavior

Take a benign Office document containing a macro in an isolated lab environment.

Try to determine:

* Which internal stream contains the VBA project?
* What commands does the macro execute?
* Does it access the filesystem?
* Does it invoke PowerShell?
* Does it communicate over the network?

---

## Practice 2 — Trace a Download Chain

Create a harmless PowerShell script that:

```text
Requests a test resource
        ↓
Saves it to a temporary location
        ↓
Prints the saved filename
```

Then identify the same behavioral stages from an analyst's perspective.

The objective is to recognize the sequence rather than the exact commands.

---

## Practice 3 — Explore INetSim

In an isolated REMnux lab:

1. Start INetSim.
2. Generate a harmless HTTP request.
3. Inspect the resulting connection report.
4. Identify the requested URL.
5. Identify the HTTP method.
6. Locate the corresponding entry in the report.

---

## Practice 4 — Build a Process Tree

Using a memory image and Volatility 3:

1. Generate a process listing.
2. Generate a process tree.
3. Compare the two outputs.
4. Pick one suspicious process.
5. Investigate its parent process.
6. Investigate its command line.
7. Investigate its loaded modules.

The goal is to move from a **process name** toward a **behavioral understanding**.

# Key Takeaways

The major lessons from this room are:

1. **REMnux provides a specialized malware-analysis environment.**
2. **Office documents can contain executable or script-based content.**
3. **`oledump.py` can help reveal internal streams and VBA projects.**
4. **Macros can act as an initial execution mechanism for a larger attack chain.**
5. **PowerShell is a legitimate administration tool that can also be abused by malware.**
6. **CyberChef can help reverse simple obfuscation and transformations.**
7. **INetSim can provide a controlled simulated network for dynamic analysis.**
8. **Volatility 3 can extract valuable evidence from memory images.**
9. **Process relationships are often as important as individual process names.**
10. **Evidence pre-processing makes large investigations faster and more repeatable.**
11. **`strings` can provide useful investigative clues from binary or memory data.**
12. **The strongest investigations correlate static, dynamic, network, and memory evidence.**

## Final Perspective

The REMnux Getting Started room provides a useful first exposure to a professional malware-analysis workflow.

A suspicious file should not be treated as an isolated object. It may be part of a sequence involving macros, scripts, downloaded payloads, processes, network communication, and memory-resident artifacts.

Learning to connect these pieces is one of the foundations of effective malware analysis and incident response.
